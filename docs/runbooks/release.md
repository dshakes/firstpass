# Runbook: cutting a release

Firstpass releases are built by [`cargo-dist`](https://opensource.axo.dev/cargo-dist/),
configured in [`dist-workspace.toml`](../../dist-workspace.toml) and driven by
[`.github/workflows/release.yml`](../../.github/workflows/release.yml)
(autogenerated by `dist` — **do not hand-edit**, and see the warning below about
what happened when someone did). Releases through `v0.3.0` have shipped on all
channels; this runbook is the procedure that produced them.

The tag push in step 4 is the trigger for a real GitHub release with
downloadable artifacts. **Treat it as a human-gated action** — nothing in CI
pushes a version tag on its own, and you should not automate that step
without deciding to.

> ### Why the tag must be pushed by a human, not a workflow
>
> This is not a style preference; it is the whole mechanism. GitHub's recursion
> guard means **an event created with `GITHUB_TOKEN` starts no workflow run**. A
> workflow that pushes `refs/tags/vX.Y.Z` on your behalf therefore triggers
> *nothing* — not `Release`, not `docker`, not `crates-io`, not `python-wheels` —
> and reports success while doing it.
>
> `v0.3.0` was first cut that way. It produced a public GitHub Release with **zero
> assets**, every channel still on the previous version, and `latest` serving the
> old image. No job failed. No check went red. The only way to notice was to look
> for runs that should have existed and find none.
>
> If you ever replace `release.yml` with something that pushes its own tag, you
> will reproduce this exactly.

> ### The workflow that runs is the one AT THE TAG
>
> Actions resolves the workflow file from the tagged ref, not from `main`. So a
> tag must point at a commit that already contains the release workflow you expect
> to run. Re-pushing an old tag after fixing `release.yml` on `main` rebuilds
> nothing, because the tagged commit still holds the broken file. Move the tag to
> the fixed commit.

## Prerequisites

- `dist` installed locally and matching the pinned version in
  `dist-workspace.toml` (`cargo-dist-version = "0.32.0"`):
  ```bash
  cargo install cargo-dist@0.32.0 --locked
  dist --version   # should print: cargo-dist 0.32.0
  ```
- Push access to `main` and permission to push tags (this is the
  human-gated step — see above).
- A clean `main` at the commit you intend to release: `git status` shows
  nothing pending, and CI (`ci.yml`, `audit.yml`) is green on that commit.
## Distribution channels & required secrets

A tagged release drives **eight** channels. They are all wired and locally
verified; each registry push is gated on an operator secret, and the build for
that channel still runs (producing artifacts) even when the secret is absent —
only the push is skipped. Set the secret to light the channel up.

| Channel | Built by | Push gated on |
| --- | --- | --- |
| Prebuilt binaries, `curl \| sh`, PowerShell | cargo-dist (`release.yml`) | nothing — attaches to the GitHub Release |
| Docker / GHCR | `docker.yml` | nothing — built-in `GITHUB_TOKEN` |
| Homebrew | cargo-dist `publish-homebrew-formula` → `dshakes/homebrew-tap` | **`HOMEBREW_TAP_TOKEN`** (tap repo already exists) |
| npm | `npm-publish.yml` (OIDC trusted publishing) | an npm **Trusted Publisher** for the package → workflow `npm-publish.yml` (no token) |
| pip / uvx (wheels) | maturin (`python-wheels.yml`), trusted publishing | repo var **`PUBLISH_TO_PYPI=true`** + a PyPI pending publisher (no token) |
| crates.io (`cargo install firstpass-proxy`) | `crates-io.yml` (core→proxy) | repo var **`PUBLISH_TO_CRATES=true`** + **`CARGO_REGISTRY_TOKEN`** |

Installed binaries also carry a self-updater (`install-updater = true`): users
run `firstpass-proxy-update` to pull the latest release in place.

`cargo install --git` and Docker `:latest` (on `main`) already work with no
release. The `dist plan` / build steps below cover the cargo-dist channels; the
maturin wheels build in parallel off the same `v*` tag.

## 1. Confirm the plan

Run `dist plan` from the repo root and read the output — it tells you exactly
what `dist` thinks it will build for the next release without touching
anything:

```bash
dist plan
```

`dist plan` also runs on every PR as the `plan` job, so this drift cannot go
unnoticed for long — **and when it does report drift, read it rather than
classifying it as intentional.** A hand-written `release.yml` once replaced the
generated one; `dist plan` said `release.yml has out of date contents` for weeks
and it was treated as deliberate divergence. It was not drift. It was the entire
artifact pipeline being gone, which only surfaced when a release shipped with no
binaries in it.

**How you know it worked:** the output lists the workspace version
(`Cargo.toml` `[workspace.package] version`), the release
target triples from `dist-workspace.toml`
(`aarch64-apple-darwin`, `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`,
`x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`), and the app(s) it will
package. If `dist plan` errors, fix that before touching a version or a tag —
the CI run will hit the same error.

## 2. Bump the version

Bump `version` in `[workspace.package]` in the root [`Cargo.toml`](../../Cargo.toml)
(every crate under `crates/*` inherits it via `version.workspace = true`).
Commit that as a normal PR-reviewed change, merged to `main` like any other:

```bash
git checkout -b release/vX.Y.Z
# edit Cargo.toml: version = "X.Y.Z"
cargo fmt --all --check   # confirm the bump didn't touch formatting
git commit -am "chore: bump version to X.Y.Z"
git push -u origin release/vX.Y.Z
# open a PR, get it reviewed and merged to main
```

## 3. Re-run the plan against the merged commit

```bash
git checkout main && git pull
dist plan
```

**How you know it worked:** `dist plan` now reports the new `X.Y.Z` version.

## 4. Tag and push — the human-gated trigger

`release.yml` triggers on a version-shaped tag push (see the `on:` block in
that file). Tag the exact commit that merged the version bump:

```bash
git tag vX.Y.Z
git push origin vX.Y.Z
```

This is the irreversible, outward-facing step: pushing the tag starts a
public GitHub Actions run that, on success, publishes a GitHub Release with
downloadable artifacts. Don't do it as a side effect of anything else, and
don't script it into an unattended pipeline.

## 5. Watch the release workflow

Open the Actions tab (or `gh run watch`) for the `release` workflow run
triggered by the tag push. It builds each target, generates checksums and
installer scripts, and (only after the plan/build/host jobs succeed)
publishes the GitHub Release.

**How you know it worked:** green is not the test — the first `v0.3.0` attempt was
green and shipped nothing. **Count the assets:**

```bash
gh release view vX.Y.Z --json assets -q '.assets | length'          # expect ~23
gh run list --limit 10 --json workflowName,headBranch,conclusion \
  -q '.[] | select(.headBranch=="vX.Y.Z") | "\(.workflowName): \(.conclusion)"'
```

A release with **0 assets** means the tag triggered nothing (see the warning at
the top) or the workflow at the tag was not the cargo-dist one. Both look like
success from the Actions tab.

## 6. Verify artifacts and checksums

Download an artifact for your platform and verify it against the published
checksum before telling anyone it's ready:

```bash
curl -LO https://github.com/<org>/firstpass/releases/download/vX.Y.Z/<artifact-name>
curl -LO https://github.com/<org>/firstpass/releases/download/vX.Y.Z/<artifact-name>.sha256
shasum -a 256 -c <artifact-name>.sha256
```

**How you know it worked:** `shasum` prints `OK`. Then actually run the
binary — `firstpass doctor` against a known-good config — before considering
the release verified, not just downloaded.

## 6b. Confirm every channel actually published

Each channel fails independently and quietly. Check them by their own evidence,
not by the release workflow being green.

```bash
# every workflow the tag should have triggered
gh run list --limit 10 --json workflowName,headBranch,conclusion \
  -q '.[] | select(.headBranch=="vX.Y.Z") | "\(.workflowName): \(.conclusion)"'
# expect: Release, docker, crates-io, python-wheels

# npm runs LATER — on `workflow_run` after Release completes at a v* ref
gh run list --workflow=npm-publish.yml --limit 2 \
  --json event,conclusion -q '.[] | "\(.event): \(.conclusion)"'

# the image must be dual-arch on BOTH tags
for t in vX.Y.Z latest; do docker manifest inspect ghcr.io/dshakes/firstpass:$t; done
```

Three failure modes seen in practice, none of which turned a check red:

- **npm `skipped`.** Its condition requires the `Release` run's `head_branch` to
  start with `v`. A release workflow that runs on `main` and tags from inside
  itself yields `head_branch: main`, so npm skips every time.
- **npm `no assets to download`.** It pulls `*-npm-package.tar.gz` from the
  release's assets. No artifacts means no npm, regardless of triggers.
- **`latest` on the wrong architecture.** `docker.yml` gates `latest` on
  `startsWith(github.ref, 'refs/tags/v')` precisely because non-tag builds are
  amd64-only. If the tag did not trigger `docker`, `latest` silently keeps
  serving the previous release — this shipped once already.

The `Release` workflow's name is load-bearing: `npm-publish.yml` waits on
`workflow_run: workflows: ["Release"]`, and that match is **case-sensitive**.
Renaming the workflow breaks npm with no error anywhere.

## 7. Registry channels (Homebrew, npm, pip, crates.io)

`homebrew` and `npm` are already in `installers` (`dist-workspace.toml`) and
their publish jobs are in `release.yml`; pip/uvx wheels build via
`python-wheels.yml`. Each is a no-op until its secret exists (see *Distribution
channels & required secrets* above). To light one up:

- **Homebrew:** the tap repo `dshakes/homebrew-tap` already exists (shared with
  distil/compass). The secret is named **`HOMEBREW_TAP_TOKEN`** — cargo-dist reads
  exactly that name and generates the formula itself, so the repo needs no
  `Formula/*.rb` checked in. (A hand-written release job once looked for
  `HOMEBREW_TAP_PAT` and a committed `Formula/*.rb`; neither exists, so it skipped
  every release with a warning nobody read.) Add it with push access to the tap;
  the next tag pushes `Formula/firstpass.rb` and users `brew install
  dshakes/tap/firstpass`.
- **npm:** OIDC trusted publishing (no token). On npmjs.com → the package →
  Trusted Publisher → GitHub Actions: org `dshakes`, repo `firstpass`, workflow
  `npm-publish.yml`, environment blank, allowed action `npm publish`. The npm
  package builds via cargo-dist and `npm-publish.yml` pushes it on release.
- **pip / uvx:** register a PyPI trusted publisher (project `firstpass`, repo
  `dshakes/firstpass`, workflow `python-wheels.yml`, environment `pypi`), then
  set repo variable `PUBLISH_TO_PYPI=true`. No long-lived token — OIDC only.
  The tag build publishes wheels for all five targets + sdist, then `pip install
  firstpass` / `uvx firstpass`.
- **crates.io:** set repo variable `PUBLISH_TO_CRATES=true` and a
  `CARGO_REGISTRY_TOKEN` secret. `crates-io.yml` publishes `firstpass-core`
  first, waits for the index, then `firstpass-proxy`. `firstpass-bench` is
  `publish = false`.

## Rollback: pin to a prior version

There is no "undo" for a published GitHub Release short of manually marking
it a draft/pre-release or deleting it (deleting a public release is a
destructive, outward-facing action — confirm with whoever owns the repo
before doing it, and prefer *not* deleting: yank forward with a fixed
release instead of erasing history people may already be pinned to).

To roll a deployment back to a known-good prior version:

1. Identify the last good tag (e.g. `vX.Y.Z-1`).
2. Re-download that release's artifact directly from
   `https://github.com/<org>/firstpass/releases/tag/vX.Y.Z-1` and verify its
   checksum the same way as step 6.
3. Redeploy that binary. If the bad release already reached production,
   also flip to observe mode while you sort it out — see
   [`docs/runbooks/soak.md`](soak.md) rollback section.
4. If the broken release must not be installed by new users going forward,
   mark it `Pre-release` (not delete) in the GitHub UI and note the issue in
   the release notes of the next good tag.
